Two numbers, because a gentle pan leaves idle frames and a continuous render doesn’t. Both tables render the same fixed graph and both are interactive — the difference is cadence. Renderers that repaint only when the view changes — Sigma, Helios, deck.gl — skip the idle frames a gentle pan leaves, so they sit at the display refresh: that number is smoothness plus a free idle (a real advantage for a mostly-static graph), not render throughput. Forced to repaint every frame at the full 1.16M-edge tier, Sigma drops 120→40, Helios 116→58 (91 in fast-edge mode) and deck.gl 120→67, while Cosmograph moves least (50.5→34 — it repaints every frame by architecture, so it never had an idle discount to lose). At the smaller tiers the gap only opens at 615K edges, where Sigma reads 78 continuous against deck’s and Helios’s vsync-capped 120.
The linkBlending picture changed once antialiasing was equalised: with MSAA off, turning link alpha-blending off (Cosmograph · opaque, linkBlending:false — a cosmos.gl 3.1 engine setting) lifts the wrapper’s full-tier numbers ~1.6–1.8× (pan 50→91, continuous 34→55 at 1.16M) and is near parity at 615K, where both configurations run close to the display cap; on the bare 3.1 engine the two modes now measure within noise. Much of the 3–5× lift measured before the antialiasing equalisation was multisample resolve amplifying blend cost, not blending alone. The trade-off stands: overlapping links no longer darken (no density shading).
Context antialiasing is equalised — and it matters more than any library choice: Sigma hardcodes antialias:false and cannot enable it, so deck.gl and Helios are configured the same way (both engines expose the setting). Before that equalisation, multisample resolve dominated their every-frame numbers — an A/B at 615K edges moved deck.gl’s continuous figure from 26 to the 120 vsync cap and Helios’s from 36 to 120. The cosmos.gl engine exposes no antialias setting, so its rows get the same treatment via a page-level context shim (the canvas’s first getContext call pre-sets antialias:false before the engine’s own request) — the A/B that motivated it moved Cosmograph’s 615K pan from 25 to 112. Every published row now renders without multisample cost; a real engine setting would make the shim unnecessary.
At 16.5M edges the field separates — and one library stops running. Up to 1.16M edges every on-demand renderer pans at the display refresh; at cit-Patents’ 16.5M edges the pan column spreads across an order of magnitude and Sigma.js exhausts the browser’s memory during load and never renders a frame (it already holds ~711 MB of graphology objects at 1.16M edges; the crash is the honest result, so the cell reads ✕ rather than a number). Among the survivors, Helios-Web’s fast-edge mode leads the pan at ~37 fps and deck.gl follows at ~14 — on 476 MB against Helios’s 4.7 GB and the cosmos family’s 2.7–4.2 GB. Cosmograph’s profile here differs in kind rather than degree: its median frame is 8.3 ms (display-cap speed) but a few multi-second stalls drag the wall-clock average to ~3 fps — bursts of smooth rendering punctuated by freezes, not steady slowness. The ranking at this tier is not the ranking below it: the engines that lead the small tiers are not the ones that survive the large one.
A separate axis from rendering. Everything above uses precomputed node positions, to isolate rendering — but computing that force-directed layout is itself a cost, and where it runs (GPU or CPU) determines how it scales. The render benchmark sets this aside, so it is measured here. Below: force-layout throughput on synthetic graphs — the GPU force simulations (cosmos.gl, Helios) against the CPU force-atlas (graphology FA2) that produces the “precomputed” positions in the first place.
Running the force simulation on the GPU computes the layout roughly 25–40× faster than the CPU force-atlas at these scales — 39 vs 1.6 iters/sec at 100K nodes, 9.7 vs 0.23 at 500K — and continues to 4M nodes (~1.2 iterations/sec — the scale of the cit-Patents tier, whose layout was computed this way), where the CPU approach is wholly impractical (minutes per iteration, blocking the main thread). It is also incremental: the GPU sim renders each step, so the graph settles on screen, where the CPU force-atlas blocks until it finishes. For a graph whose positions are already computed, the render figures above apply instead — a different question with a different answer.

Key findings

  • With rendering state equalised, deck.gl renders the 1.16M-edge overview every frame at 67 fps and Helios’s fast-edge mode at ~91 — ahead of Sigma (~40), whose strength is the pan path: repaint-on-demand smoothness at the display refresh, at every tier it can load.
  • Scale is where the field separates, and memory is why: at 16.5M edges deck.gl draws the graph in 476 MB while Helios needs 4.7 GB, the cosmos family 2.7–4.2 GB, and Sigma exceeds the browser’s limit and crashes. The data model, not shader speed, decides who is still running at the top tier.
How each library is configured (and how it repaints)
  • Sigma.js — thin feathered edges (1.7 px — Sigma’s default minimum thickness; edges are given no explicit width), repaint-on-demand (idle frames cost nothing), precomputed FA2 layout, no label data (Cosmograph, by contrast, renders its default labels), context antialiasing off (Sigma hardcodes antialias:false; deck.gl and Helios are configured to match — see the antialiasing note above; the cosmos.gl engine cannot disable it).
  • Helios-Web — its DEFAULT edge mode: alpha-blended, variable-width edge quads (width follows node size), repaint-on-demand, precomputed layout. Helios-Web · fast is the same page with fastEdges on — 1px GL-line edges, the lighter mode. Both rows render with context antialiasing off (see below).
  • deck.gl — LineLayer over binary typed-array buffers, repaint-on-demand, precomputed layout.
  • Cosmograph — the product (duckdb-wasm data prep, labels, hover / link-picking) on the cosmos.gl engine, GPU simulation disabled (precomputed layout); redraws every frame (continuous), default alpha-blended links; antialiasing disabled via the page-level context shim (the engine has no setting).
  • Cosmograph · opaque — the same, with link alpha-blending turned off (linkBlending:false, a cosmos.gl 3.1 engine setting) — a ~3× lift on the dense-overview pan; the cost is losing the density shading of overlapping links.
  • The two fps columns: gentle pan = a ~30 events/s pan (renderers that repaint only on change idle at the display refresh between events); continuous = force-repaint the fixed overview every frame (median of 3), so every engine renders every frame. Sigma and the cosmos-family rows are driven by an imperceptible camera nudge (their public render calls re-index or re-ingest data — a data cost, not a render cost); deck and Helios by their plain redraw calls. The pointer rests off-canvas during the continuous runs, so no engine pays hover-picking costs there.
  • The 16.5M-edge tier ships as binary buffers (positions, edges, colours) rather than JSON, which would be ~450 MB of parse work and would measure the parser rather than the renderer; every engine reads the same buffers and then builds whatever its own data model needs — that build cost is part of what the tier measures. Its layout is a GPU force simulation (a spectral embedding seeds it, the simulation refines), since CPU force-atlas is impractical at 3.77M nodes.
  • Node sizes are each engine’s natural mapping of √degree, which differ in pixel terms (up to ~4× total node area between engines — Sigma/deck largest, the cosmos family smallest after its size compression). Edges dominate the frame at these scales, so this is second-order; edge style is the cost driver.
How it was measured — the five gates
  • Real GPU, verified: every run checks it ran on Apple-Silicon hardware (Metal GPU), never a software fallback.
  • Coverage: the engine must actually load the whole dataset (engine-reported counts vs the loaded file).
  • Presentation: the surface must actually present — a pixel-diff under a camera delta (web) or a windowed swapchain, not an offscreen loop (native). This is what corrected the "200 fps @50M" Datoviz figure to its real windowed 5 fps.
  • Camera-state: every number records the camera state it was measured in (here: the full-graph overview / orbit).
  • Input-honesty: motion is engine-API driven, not a synthetic uncoalesced event stream (the artifact that once mis-scored Cosmograph at 5 fps).
  • A cell is published only if all five gates pass; a failure quarantines the number, it is never silently shown.
