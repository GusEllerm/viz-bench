Two numbers, because a gentle pan leaves idle frames and a continuous render doesn’t. Both tables render the same fixed graph and both are interactive — the difference is cadence. Renderers that repaint only when the view changes — Sigma, Helios, deck.gl — skip the idle frames a gentle pan leaves, so they sit at the display refresh: that number is smoothness plus a free idle (a real advantage for a mostly-static graph), not render throughput. Forced to repaint every frame at 369K edges, Sigma drops 120→87, Helios 119→70 and deck.gl 120→49, while Cosmograph barely moves (33→27 — it already repaints every frame, so it never got the idle discount). At the full 1.16M-edge tier the graph is dense enough that the pan itself falls below the refresh for every engine, and the two numbers converge (Sigma reads 30 on both).
The linkBlending lift is strongest where it matters — the dense-overview pan: turning link alpha-blending off (Cosmograph · opaque) lifts the gentle-pan overview ~3× — 24→76 fps at 615K edges and 10→30 at 1.16M (linkBlending:false, a cosmos.gl 3.1 engine setting). Under forced every-frame rendering the lift shows at the mid tiers (27→35 at 369K, 19→25 at 615K) and washes out at 1.16M, where both configurations sit at ~6–7 fps. The trade-off: overlapping links no longer darken (no density shading).
A separate axis from rendering. Everything above uses precomputed node positions, to isolate rendering — but computing that force-directed layout is itself a cost, and where it runs (GPU or CPU) determines how it scales. The render benchmark sets this aside, so it is measured here. Below: force-layout throughput on synthetic graphs — the GPU force simulations (cosmos.gl, Helios) against the CPU force-atlas (graphology FA2) that produces the “precomputed” positions in the first place.
Running the force simulation on the GPU computes the layout roughly 25–40× faster than the CPU force-atlas at these scales — 39 vs 1.6 iters/sec at 100K nodes, 9.7 vs 0.23 at 500K — and continues to 1M, where the CPU approach is impractical (minutes per iteration, blocking the main thread). It is also incremental: the GPU sim renders each step, so the graph settles on screen, where the CPU force-atlas blocks until it finishes. For a graph whose positions are already computed, the render figures above apply instead — a different question with a different answer.

Key findings

  • Sigma leads both metrics, and its edge is a real rendering one, not just an idle one: forced to render the 1.16M-edge overview every frame it still holds 30 fps (hairline edges) — ~2.4× Helios (12.5) and deck.gl (11), with Cosmograph at ~6–7.
  • Resource cost splits the field: deck.gl is featherweight (43 MB at 1.16M edges — binary typed-array buffers) while Sigma trades ~711 MB for its speed.
How each library is configured (and how it repaints)
  • Sigma.js — 1px hairline edges, repaint-on-demand (idle frames cost nothing), precomputed FA2 layout.
  • Helios-Web — WebGL 1px fast-edge mode, repaint-on-demand, precomputed layout.
  • deck.gl — LineLayer over binary typed-array buffers, repaint-on-demand, precomputed layout.
  • Cosmograph — the product (duckdb-wasm data prep, labels, hover / link-picking) on the cosmos.gl engine, GPU simulation disabled (precomputed layout); redraws every frame (continuous), default alpha-blended links.
  • Cosmograph · opaque — the same, with link alpha-blending turned off (linkBlending:false, a cosmos.gl 3.1 engine setting) — a ~3× lift on the dense-overview pan; the cost is losing the density shading of overlapping links.
  • The two fps columns: gentle pan = a ~30 events/s pan (renderers that repaint only on change idle at the display refresh between events); continuous = force-repaint the fixed overview every frame via each engine’s own render call (median of 3), so every engine renders every frame.
How it was measured — the five gates
  • Real GPU, verified: every run checks it ran on Apple-Silicon hardware (Metal GPU), never a software fallback.
  • Coverage: the engine must actually load the whole dataset (engine-reported counts vs the loaded file).
  • Presentation: the surface must actually present — a pixel-diff under a camera delta (web) or a windowed swapchain, not an offscreen loop (native). This is what corrected the "200 fps @50M" Datoviz figure to its real windowed 5 fps.
  • Camera-state: every number records the camera state it was measured in (here: the full-graph overview / orbit).
  • Input-honesty: motion is engine-API driven, not a synthetic uncoalesced event stream (the artifact that once mis-scored Cosmograph at 5 fps).
  • A cell is published only if all five gates pass; a failure quarantines the number, it is never silently shown.
